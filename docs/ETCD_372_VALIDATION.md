## Fresh deployment, not a data migration

The old Bitnami 3.5.17 cluster and the old Milvus deployment were stopped only
after the isolated candidate passed its tests. Private resource manifests and
old PVCs remain preserved. No old etcd data directory was opened by 3.7.2.

- New etcd volume claim template: `etcd-data-v37`.
- New Milvus PVC: `openserverless-milvus-etcd37`.
- New Milvus etcd and S3 metadata/object prefixes: `milvus-etcd-v37`.
- Canonical Service names and application endpoints are preserved.
- Existing synthetic tenants were provisioned through OPS with the same identities
  and credentials; new application fixtures were generated by the unchanged apps.

Automatic replacement of an existing etcd image, membership, cluster identity,
PVC layout or root credentials is refused before key/account mutation. Orphaned
3.7 PVCs are refused as well. Milvus similarly refuses implicit TLS, endpoint,
metadata prefix, WAL or volume changes. Old preserved volumes represent the
previous installation's recovery point, not a rollback of newly written data.
Migration and `ops setup cluster --upgrade` remain deferred.

## Native image and authentication integration

The upstream image has no shell and does not implement Bitnami initialization.
OPS now renders native server arguments, generates per-installation TLS and JWT
keys, bootstraps authentication over mTLS, and manages users through the verified
TLS JSON gateway. The repository's previously shared JWT private key is removed.

Both client and peer transport require verified certificates and TLS 1.3.
Services remain ClusterIP. Pods run as UID/GID 1001, without service-account token,
with a read-only root filesystem and dropped capabilities. Milvus mounts only the
client certificate material, with group-readable mode 0440 and fsGroup 999.
The client certificate has no Common Name that could impersonate an RBAC user;
username/password authentication remains required.

Readiness/startup/liveness require **authentication enabled and healthy quorum**.
Raw `etcdctl endpoint health` alone also succeeds before auth is enabled, so it
is insufficient as an installation readiness gate.

The 3.7 JSON gateway can return errors in `message` rather than `error`, and
missing credentials can produce HTTP 400 rather than 401/403. Tests check actual
denial and absence of values. Auth-store changes can invalidate an existing JWT;
OPS renews only the affected session's own credentials, once, for the specific
stale-revision/invalid-token errors. Permission failures are never retried with
administrator credentials.

TLS material is preserved on reconciliation; incomplete or missing material on
an active deployment fails closed. Leaf certificates last 730 days and the CA
3650 days. Automated certificate renewal and credential rotation are not
implemented by this modernization step and need a separate operational design.

## Validation evidence

- 47 Python unit tests: rendering, storage guards, TLS generation, refusal of
  credential resets, session refresh, Milvus, and existing S3 protection tests.
- Six Go probe scenarios: auth enabled, disabled, missing/malformed status,
  unavailable auth status, unavailable quorum.
- 21 live etcd checks, repeated on the installed canonical cluster: auth, mTLS,
  transactions/CAS, expiring leases, prefix-scoped users, idempotent provisioning,
  peer read/write denial, tenant deletion and invalidation of deleted credentials.
- 23 live Milvus checks on both isolated and installed clusters: own data access,
  peer isolation, denied administration/anonymous requests, immediate write/read,
  tenant creation/deletion/recreation and empty recreated databases.
- Candidate auth-disable test: the probe rejects the member, then OPS restores auth.
- Candidate member restart, deliberate quorum loss/recovery, rolling cluster restart
  and Milvus restart: durable etcd keys and both synthetic tenant fixtures survive.
- Canonical cluster: all three members report 3.7.2, agree on one leader, and return
  identical KV hashes at the same revision. Configured root credentials were absent
  from server logs; raw logs and secret-bearing manifests remain private.
- Existing S3 regression probe: 12/12, including owner/peer permissions, denied
  anonymous data/list/write, public web reads, grant revocation and private bucket reuse.

## Alpha/Beta and installed-cluster restart

The complete unchanged application suite passed 15/15 checks twice after installation,
including after a rolling restart of the installed etcd cluster and a Milvus restart.
Each run used 100 requests per tenant at concurrency 4, with zero errors.
An independent observer inspected both previously written fixtures at the first
Milvus Ready state (23.84 seconds from observer start); all five data services
returned accepted results. Nine earlier samples had HTTP health before Milvus
recovery compliance was Ready, confirming why health alone is insufficient.
Alpha/Beta source and deployed validation-action fingerprints remained identical.

End-to-end timings in milliseconds (100 samples per cell):

| Run | Alpha p50 / p95 | Beta p50 / p95 | Errors |
| --- | --- | --- | --- |
| Before, etcd 3.5.17 | 272.6 / 357.6 | 267.2 / 327.5 | 0 |
| After, etcd 3.7.2 | 280.0 / 402.1 | 272.0 / 338.7 | 0 |
| After installed-cluster restart | 254.9 / 320.7 | 261.5 / 315.8 | 0 |

These samples support compatibility and reveal no persistent end-to-end latency
regression. They do not establish an etcd-specific performance gain: the new
installation has fresh metadata, cache state varies, and the first post-install
run overlapped the dedicated backend lifecycle checks. The final run was separate.
The lab has one K3s node; process/quorum recovery tests do not establish host-level
high availability.
